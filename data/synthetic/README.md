# Synthetic Dataset — ReconcileAI

Generated by `generator.py`, fixed seed `20260825` (`DEFAULT_SEED`). Every record in this dataset is **simulated** — no real financial data is used anywhere in this project (see `CLAUDE.md`).

Regenerate with:

```
python data/synthetic/generator.py            # uses DEFAULT_SEED
python data/synthetic/generator.py 12345       # or an explicit seed
```

This writes seven files to `data/synthetic/seeds/`: `orders.json`, `payments.json`, `settlements.json`, `bank_transactions.json`, `refunds.json`, `fee_rules.json`, `ground_truth.json`, plus `GENERATION_INFO.json` recording the seed and archetype counts used. Regenerating with the same seed produces byte-identical files (verified in `backend/tests/test_generator.py`).

## Scale

**300 records**, where a "record" is one `Order` — the primary unit `ground_truth.json` is indexed by. Each order has an associated `Payment`, and (depending on its archetype) zero or more `Settlement`, `BankTransaction`, and `Refund` rows.

## Deliberate modeling choices

- **UPI is modeled at zero MDR/fixed-fee/tax** (matching the real-world zero-MDR treatment of UPI in India under current RBI/NPCI rules) and is used as the baseline method for every archetype **except** `fee_mismatch`, so each archetype demonstrates exactly one anomaly at a time instead of confounding fee behavior with whatever else the case is testing. `fee_mismatch` specifically uses the card fee rule (1.8% MDR + ₹2 fixed + 18% tax on the fee) to produce a genuine, verifiable deduction. **Fee figures are illustrative** for demo purposes and are not asserted to be Razorpay's actual published rates.
- **Currency is restricted to INR only** in this dataset and in the validation schemas (`backend/app/schemas/records.py`) — multi-currency conversion is explicitly out of scope for the MVP (see `RECONCILEAI_CONTEXT_PACK.md`).
- **Primary IDs are never "mangled"** — `order_id`/`payment_id`/etc. are always well-formed; only human-entered reference-ish fields (`utr_reference`, `narration`) are ever noisy. A subset of `exact_match` cases (~10%, seed-determined) have whitespace/case noise injected into their raw `utr_reference` that `app.engines.normalization.normalize_reference` collapses back to the canonical form — proving normalization does something. `reference_mismatch` cases, by contrast, have a **genuinely unrelated** reference that survives normalization untouched, since that's the point of the archetype.
- **`reference_mismatch` vs `unexplained_difference` vs `under_settlement`** are deliberately distinguished so each has an unambiguous root cause for future evaluation: `reference_mismatch` has correct amounts but a bad reference key; `under_settlement` is internally consistent (its own fee/tax math balances) but short relative to the payment; `unexplained_difference` is short in a way that doesn't even reconcile against its **own** stated fee/tax fields — a data-integrity anomaly, not just a shortfall.

## Ground truth (`ground_truth.json`)

One entry per order:

```json
{
  "order_id": "ORD-00001",
  "archetype": "fee_mismatch",
  "category": "fee_mismatch",
  "true_matches": {
    "payment_id": "PAY-00001",
    "settlement_ids": ["STL-00001"],
    "bank_txn_ids": ["BANKTXN-00001"],
    "refund_ids": []
  },
  "expected_action": "auto_resolve",
  "is_adversarial": false,
  "notes": "Net settlement equals payment amount minus the card MDR + tax per FEE-CARD-001; verifiable exactly."
}
```

`category` is `null` for `exact_match` (a clean match is not a kind of exception). `expected_action` is one of `auto_resolve` / `human_review` / `unresolved` and is **only for the evaluation harness** (a later milestone) — it is never given to the matching/exception/AI engines themselves. `is_adversarial` flags the 5 designed-to-trap cases.

## What this milestone does NOT include

No matching, exception-detection, evidence-collection, AI investigation, confidence scoring, policy, or audit logic reads or writes this dataset yet — this milestone only generates it, validates it, normalizes it, and ingests it into the database. Those engines are later milestones (see `PROJECT_PLAN.md`).
