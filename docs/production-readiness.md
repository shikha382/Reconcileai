# Production Readiness Matrix (Milestone 14)

Honest, evidence-based. Nothing below is marked READY without a specific, checkable reason. This is a hackathon submission's own self-assessment, not a claim of production deployment.

| Area | Status | Evidence / reason |
|---|---|---|
| **Configuration** | PARTIAL | `app.config.Settings`/`app.adapters.config.ProviderSettings` are fully environment-driven, no hardcoded secrets, sensible fixture-mode defaults. **Gap:** no config validation on startup (a malformed env var is only caught when first used, e.g. `int(_env(...))` raising at import time — acceptable for a single-process demo, not for a managed rollout with staged config). |
| **Secrets** | PARTIAL | Never logged, never returned in an error/health/status response, never sent to the frontend, never in an audit payload — all directly tested (`test_secret_safety.py`, `test_m14_sources_status.py`). **Gap:** no real secret-management infrastructure (Vault, AWS Secrets Manager, etc.) — plain environment variables only. Production recommendation: inject secrets via the deployment platform's own secret store, never via a committed `.env`. |
| **Provider integration** | PARTIAL | Read-only Razorpay adapter fully implemented (fixture/mock/live modes), with bounded retry, rate-limit handling, and a real provider error taxonomy. **Gap:** `live` mode has never made a real call against Razorpay's actual API in this environment — only monkeypatched HTTP responses have exercised it. No production credentials exist to change this. |
| **Validation** | READY | Every record (file-sourced or adapter-sourced) passes through the identical, already-hardened M1 Pydantic validation (`app.schemas.records`) — no bypass exists on either path (`test_end_to_end_fixture_pipeline.py` proves this for the adapter path directly). |
| **Idempotency** | READY | `session.merge()` on a deterministic canonical ID, proven for both the file-based path (M1, unchanged) and the adapter path (M14, `test_idempotency.py`) — re-ingesting identical or updated data never duplicates a row. |
| **Retries** | READY (for reads) | Bounded, exponential-backoff retries for 5xx/timeout; immediate, non-retried failure for 401/403/429 (`test_retry_and_errors.py`). No financial-mutation retry logic exists anywhere, because no financial mutation exists anywhere. |
| **Rate limits** | PARTIAL | A `429` is detected and surfaced cleanly with `Retry-After` when the provider supplies it. **Gap:** no exact Razorpay rate-limit thresholds are implemented or claimed — none are documented in the project's available reference material, and inventing one would violate the M14 brief's own "do not claim exact Razorpay limits unless supported by official documentation" instruction. |
| **Observability** | PARTIAL | `ProviderOperationLog` records provider/operation/correlation-id/duration/record-count/success/error-category per fetch, with no secret ever included. **Gap:** in-memory only, per-call, not exported to any external monitoring system (no such system exists in this hackathon environment). |
| **Audit** | READY | The existing M6 hash-chained ledger is completely unmodified by M14; adapter operations deliberately do NOT write to it (a documented scope decision, `docs/provider-adapters.md`) — audit continues to mean exactly what it meant before, for exactly the same set of financial-decision events. |
| **Authorization** | READY | The new `/sources/status` endpoint reuses the existing `Capability.VIEW_RUN` — no new capability, no new authorization mechanism, AI-actor-forbidden confirmed directly (`test_m14_sources_status.py`). |
| **Data retention** | NOT IMPLEMENTED | No retention/archival/purge policy exists for `RawRecord`, audit events, or any other table — every milestone to date has accumulated data in a single SQLite file with no expiry. Acceptable for a bounded demo dataset; not evaluated for production data volumes. |
| **Error handling** | READY | Every API error (including a framework-raised 404/405 on an unmatched route, fixed in M13) uses the same structured `{"error": {"code","message","request_id"}}` contract; every adapter error uses the parallel `ProviderError` taxonomy; neither ever leaks a stack trace, secret, or internal path (tested directly, repeatedly, across M8/M9/M13/M14). |
| **Monitoring** | NOT IMPLEMENTED | No metrics/alerting/dashboarding system (Prometheus, Datadog, etc.) is wired up. `ProviderOperationLog` and the audit ledger are the only structured operational records that exist, and neither is exported anywhere. |
| **Deployment** | NOT IMPLEMENTED | No Dockerfile, no CI/CD pipeline, no infrastructure-as-code exists in this repository. Local `uvicorn`/`npm run dev` only. |
| **Database** | PARTIAL | SQLite, by original, documented design decision (`CLAUDE.md`, 2026-08-25) — "zero-ops persistence sufficient for a ≤300-record demo dataset," schema written to be Postgres-compatible so a swap is a connection-string change if ever justified. Never tested against Postgres in this environment. |
| **Backups** | NOT IMPLEMENTED | No automated backup of the SQLite file exists. A demo re-run (`scripts/run_reconciliation.py` or a fresh `POST /runs`) regenerates equivalent state from the deterministic synthetic dataset, which is this project's actual resilience story — not backups. |
| **Disaster recovery** | NOT IMPLEMENTED | No documented recovery runbook beyond "re-run the deterministic pipeline against the same synthetic dataset," which is sufficient for this project's own reproducibility story but is not a real DR plan for live financial data. |

## Summary

Nothing in this matrix is marked READY without either (a) a passing, named test that proves it, or (b) it being unmodified, already-proven M1–M13 behavior. Every PARTIAL/NOT IMPLEMENTED row states the specific, concrete gap rather than a vague caveat — consistent with the project's own standing rule never to claim production readiness without evidence.
