# Adversarial Evaluation (Milestone 9)

M1–M8 proved ReconcileAI works on a clean, representative 300-record dataset. M9 asks a different question: **can it be fooled?** This document covers the adversarial mutation framework, the 14 attack categories tested, the safety invariants enforced, the metrics computed, and — most importantly — the two genuine defects this evaluation found and fixed.

## Mutation framework

`backend/tests/adversarial/helpers.py` clones real M1 dataset records (`Payment`, `Settlement`, `BankTransaction`, `Refund`, `FeeRule` — via a generic `clone()` that reads every mapped column off a real record and builds a fresh, session-less instance) and mutates the clones. No independent fake financial model was built — every scenario starts from a genuine base record (usually picked by archetype via `pick_by_archetype(ground_truth, archetype, index)`), consistent with the brief's own instruction to reuse existing synthetic records wherever possible.

Two run modes, chosen per scenario for speed:
- `analyze(dataset, payment_id)` — runs M2+M3 (`run_exception_intelligence`) over the whole mutated dataset and returns one payment's `EvidenceBundle`. Fast; used when only matching/classification behavior is under test.
- `decide_one(dataset, payment_id, decision_env)` — runs the full M4–M6 decision pipeline (`run_decision_pipeline`) for exactly one exception, using a shared `DecisionEnvironment` (ledger/session/provider/approval store) so a whole adversarial suite doesn't pay the cost of re-running AI investigation across all 300 records per scenario.

Each scenario is described by a `Scenario` dataclass (`scenario_id`, `base_record_id`, `mutation_type`, `description`, `expected_safety_outcome`, `severity`) per the brief's own required shape.

## Two genuine defects found and fixed

Per the brief's explicit instruction — stop, root-cause, fix the smallest layer, add a regression test, rerun everything — both of the following were found empirically by these adversarial tests, not designed in advance.

### 1. Duplicate refund records could corrupt the reported residual (real bug, contained by defense-in-depth)

**Found by:** `test_refund_manipulation.py::test_05_duplicate_refund_only_one_real_debit_is_not_silently_doubled`.

`app.engines.reconciliation.verification.verify_refund_consistency` matched each refund record against *any* debit bank transaction of the same amount, without tracking which debits had already been claimed. Two refund records (e.g. a duplicated/replayed refund row) could both cite the *same single real debit* as independent evidence, making `decompose_discrepancy`'s reported `residual`/`fully_explained` fields look more complete than the real bank evidence actually supported.

**Verified impact:** constructed the exact worst case (a real shortfall exactly double a single real refund, duplicated) and confirmed `decomposition.residual` did drop to a false `0.00`. However, tracing `app.engines.root_cause.result.determine_root_cause`, this reported residual is **only used for explanatory detail or to distinguish `PARTIALLY_EXPLAINED` vs. `UNEXPLAINED` within an already-`MISMATCH`-status M2 result** — it is never what promotes a result to `VERIFIED`. `VERIFIED` requires M2's own `status == MATCHED`, which is computed independently of this decomposition and was unaffected. End-to-end confirmation (`decide_one`) showed the final decision stayed `HUMAN_REVIEW` throughout. So this was a real correctness/explainability defect (a wrong number shown for an already-safely-blocked case) but never crossed into an unsafe auto-resolution, verified empirically rather than assumed.

**Fix:** `verify_refund_consistency` now tracks claimed debit transactions in a set and never lets a second refund claim an already-claimed debit (`backend/app/engines/reconciliation/verification.py`).

### 2. `fee_verified` matches never cross-checked the actual bank credit (real bug, DID create unsafe auto-resolutions)

**Found by:** `test_fuzz.py::test_seeded_fuzz_never_produces_an_unsafe_auto_resolution` (seed 90210) — 7 of 60 seeded, randomized bank-credit mutations on real `fee_mismatch`-archetype records produced `SAFE_TO_RESOLVE`.

`app.engines.reconciliation.matching.resolve_single_linked_settlement`'s `fee_verified` branch checked only that the settlement's *own claimed* fields (`amount`/`fee`/`tax`/`net_amount`) were internally, mathematically consistent with the configured `FeeRule` — it never re-confirmed that the actually-credited bank amount (`bank_amount`, from `bank_credited_amount`) matched that claimed net figure. A settlement whose fee arithmetic was correct *on paper* but whose real bank credit had been separately altered or shortchanged still verified as `MATCHED` via `fee_verified`, with `financial_impact` hard-coded to `0.00` — a genuine false auto-resolution, reproduced directly (not hypothesized): a real record's confirmed credit reduced by ₹2,493.72 still reported `status=MATCHED, financial_impact=0.00`.

**Fix:** the `fee_verified` branch now also requires `bank_amount == settlement.net_amount` before declaring a match. When the fee math checks out but the confirmed credit doesn't match what that math implies was paid out, the case now correctly falls to `MISMATCH` with the real credit-vs-expected-net residual as `financial_impact` (`backend/app/engines/reconciliation/matching.py`).

**Regression impact:** re-ran the clean, unmutated 300-record dataset end-to-end after the fix — the decision distribution is **unchanged** (219 auto-resolved / 67 human review / 2 rejected / 12 unresolved, see `test_baseline_comparison.py`). Every real `fee_mismatch` record in the dataset already has a bank credit that exactly equals its settlement's net amount, so this fix closes a real gap without touching any legitimate outcome.

## Safety invariants (Phase 18)

Ten invariants, each with a standalone, directly-named test in `test_invariants.py`:

1. No negative monetary amount is ever accepted.
2. No floating-point arithmetic in authoritative financial calculations (`shared.money.quantize` refuses a raw `float`).
3. A `CONTRADICTED` verifier status can never reach `SAFE_TO_RESOLVE`.
4. A policy-blocked category can never reach `SAFE_TO_RESOLVE`.
5. Incomplete evidence can never reach `SAFE_TO_RESOLVE`.
6. An unresolved contradiction can never reach `SAFE_TO_RESOLVE`.
7. AI confidence alone can never create a resolution (`ai_confidence` is never read by `evaluate_policy`).
8. Audit-chain tampering can never report `VALID` (reconfirmed via M6's own `verify_chain`).
9. Ambiguous matching can never silently become an exact match (score threshold + margin, never a bare top-score check).
10. A replay can never create duplicate financial effects (M1's ingestion idempotency, reconfirmed).

## Results

- **399 + 43 = 442** pre-existing M1–M8 tests: all still passing after both fixes (zero regressions).
- **125 new M9 adversarial tests**, all passing, across 14 categories + invariants + matrix + classification metrics + mutation testing + fuzz + baseline comparison.
- **Unsafe auto-resolution rate: 0%** (measured directly in `test_safety_matrix.py` and `test_fuzz.py`, not asserted by assumption).
- **Critical safety failure count: 0.**
- **Exception category classification: 100% accuracy, macro-F1 1.0000** on the real, unmutated dataset (`test_classification_metrics.py`) — reconfirming M3's own established result, not a new claim.
- **Clean 300-record baseline: unchanged** (219/67/2/12) after both fixes.

## What this demonstrates

The system's layered design — deterministic matching (M2) → exception classification (M3) → AI investigation (M4, only for residual cases) → self-challenge (M6) → policy (M5, the sole decision authority) → audit (M6) — has **defense in depth**: even the duplicate-refund bug, which did produce a wrong number, was caught before it could reach an unsafe decision, because `VERIFIED` status is gated by M2's own independently-computed match status, not by M3's supplementary decomposition. The fee/bank-credit gap, by contrast, was a genuine hole in that first layer's own logic — exactly the kind of defect this milestone exists to surface, and it was fixed at its root, not papered over downstream.

## Known limitations

- The mutation/fuzz framework operates on cloned Python objects, not through the HTTP ingestion path's own JSON validation (`app.schemas.records`) — a raw-JSON-level adversarial pass (e.g. malformed currency codes at ingestion) is not covered here; M1's own validation tests already cover that layer.
- Fuzz testing (Phase 23) used one fixed seed (90210) at a manageable case count (60); it is not exhaustive, but every case is reproducible and any future failure is meant to be promoted to a permanent regression test in `test_fuzz.py`'s reserved section.
- Mutation testing (Phase 22) demonstrates sensitivity for 3 representative constants/checks (fee tolerance, exposure threshold, residual check), not an automated whole-codebase mutation score — consistent with the brief's own "do not rewrite production logic to support mutation testing" instruction.
