# Evaluation Framework

## Principle

The system must never hide an unresolved or incorrectly-handled case from its own report. The evaluation harness exists specifically to make cherry-picking impossible: it runs against the full 300-record dataset and reports every outcome, correct or not. This document was rewritten in Milestone 13 to report **actually measured** results (re-run 2026-08-29) rather than the pre-implementation methodology sketch it originally was — see `docs/demo-runbook.md` for the judge-facing summary and the claim-vs-proof matrix.

## Dataset

Generated by a deterministic, fixed-seed synthetic generator (`data/synthetic/generator.py`): `payments.json`, `settlements.json`, `bank_transactions.json`, `refunds.json`, `fee_rules.json`, plus `ground_truth.json` (never given to the matching/agent/scoring code — only to the evaluation harness, after a run completes). Audited this milestone (`scripts/audit_dataset.py`):

- 300 ground-truthed records, all order/payment/settlement/bank/refund IDs unique.
- 315 settlements, 315 bank transactions, 15 refunds (the extra settlements/bank rows are split/aggregated-settlement archetypes; 15 refunds exactly matches the 15 `refund_mismatch` records).
- 14 exception-taxonomy categories present, each with multiple instances: `aggregated_settlement` (10), `ambiguous_match` (10), `duplicate` (12), `exact_match` (138), `fee_mismatch` (18), `missing_transaction` (12), `over_settlement` (8), `partial_settlement` (12), `reference_mismatch` (12), `refund_mismatch` (15), `reversed_transaction` (7), `split_settlement` (10), `timing_mismatch` (18), `under_settlement` (8), `unexplained_difference` (10).
- 5 adversarial cases (2 `fee_mismatch`, 2 `duplicate`, 1 `ambiguous_match`), each expecting `human_review`.
- Expected-action distribution: 219 `auto_resolve`, 69 `human_review`, 12 `unresolved`.
- Zero dangling references — every settlement/bank/refund/payment ID named in ground truth actually exists in its source file.

## Reproducibility (this milestone)

Three independent full-pipeline runs against the identical dataset: every exception's category, policy decision, and financial impact were byte-identical across all three; audit event count was exactly 3,486 in all three. `run_id`/`proposal_id`/`review_id` differ every time by design (each run is its own independently-auditable record — see `CLAUDE.md`'s M7 dated decision).

## Limitations of this evaluation

- All accuracy/precision/recall/F1 figures are measured on this project's own 300-record synthetic, controlled dataset — **never claimed as a production/general accuracy guarantee**. "100%" here always means "100% on our 300-record controlled evaluation dataset."
- Performance figures use `MockAIProvider` (zero network latency) — explicitly not representative of a real LLM vendor's latency or cost.
- Matching correctness (precision/recall/F1 on the reconciliation layer) and decision safety (unsafe auto-resolution rate) are tracked as **separate** metrics deliberately — a system can match a record correctly and still make an unsafe *decision* about what to do with it (or vice versa); this project's own M9 fixes were exactly this distinction in practice (a correctly-identified `fee_mismatch` that was nonetheless being auto-resolved unsafely before the fix).
- Baseline D (LLM-only) is a proxy measurement over this project's own AI output, not an independently-built LLM-only reconciliation pipeline.

## Harness

Real, already-existing per-milestone evaluation modules, reused directly by this document's own measurement scripts rather than re-derived: `app.engines.reconciliation.evaluation.evaluate` (M2), `app.engines.exceptions.evaluation.evaluate_exceptions` (M3), `tests/audit/test_evaluation_m6.py` (M6, full-pipeline decision safety), `tests/adversarial/test_classification_metrics.py`/`test_safety_matrix.py`/`test_baseline_comparison.py` (M9). `scripts/evaluate_competitive_baselines.py` and `scripts/audit_dataset.py` (both new, Milestone 13) add the competitive-baseline and dataset-quality measurements. A milestone that regresses `incorrect_auto_resolution_rate` above 0 on the full dataset is a blocking failure, not a warning — confirmed still true and enforced by `test_evaluation_m6.py`'s own hard assertion.
