PROJECT IDENTITY
==================================================

Name:
ReconcileAI

Full name:
Deterministic-Gated Exception & Settlement Controller

Track:
Track 04 — AI Finance Controller

Core pitch:
An explainable financial reconciliation agent that uses AI to investigate difficult exceptions while deterministic verification and policy gates prevent unsafe financial decisions.

==================================================
CORE DIFFERENTIATOR
==================================================

We are NOT competing with Razorpay Recon on basic reconciliation.

Our differentiator is:

1. Root-cause diagnosis
2. Cross-source reasoning
3. Why NOT Matched negative evidence
4. AI hypothesis + deterministic verification
5. Confidence-aware resolution
6. Safe auto-resolution
7. Value-at-Risk prioritization
8. Complete auditability

==================================================
CORE PRINCIPLE
==================================================

AI PROPOSES.

DETERMINISTIC SYSTEM VERIFIES.

POLICY ENGINE DECIDES.

HUMAN APPROVES WHEN REQUIRED.

AUDIT TRAIL RECORDS EVERYTHING.

==================================================
NEVER DO
==================================================

Never allow the LLM to:

- invent financial facts
- invent evidence
- invent transaction IDs
- directly modify financial truth
- bypass policy
- mark low-confidence transactions reconciled
- fabricate confidence
- hide unresolved exceptions

Never use floating point for money.

Use Decimal.

Never claim a feature is innovative without checking Razorpay/competitor overlap.

Never add an AI component without explaining why deterministic logic is insufficient.

Never add infrastructure just because it sounds impressive.

Decision: M2's `ReconciliationStatus` (matched/partial/mismatch/ambiguous/unresolved) and M3's fine-grained `ExceptionCategory` (M1's 14-value taxonomy) are computed and reported as two SEPARATE fields, never conflated. Alternatives considered: Deriving category purely from status, or not tracking category-level detail on MATCHED records at all.
Why rejected: Would lose real information the M1 dataset actually encodes (e.g. that a cleanly-matched record was specifically a fee-adjusted or timing-delayed one) and that a future risk/reporting layer would want.

Decision: `root_cause.status == VERIFIED` is treated as the sole authoritative signal for "was this exception explained", overriding the per-candidate `NegativeEvidenceReport` when the two disagree (e.g. a split/aggregated settlement, where each individual candidate correctly fails a single-candidate `amount_balance` check even though the record IS fully reconciled via a multi-settlement sum relationship M2 already verified).
Reason: `NegativeEvidenceReport` evaluates one settlement against a payment at a time and has no concept of a multi-settlement sum relationship; `RootCauseResult` is built from M2's actual (relationship-aware) result and is therefore the more complete source of truth for "matched or not".
Alternatives considered: Making the per-candidate evidence engine relationship-aware (understand split/aggregation sums itself).
Why rejected: Would duplicate logic M2's `relationships.py` already owns; the cheaper, correct fix is for consumers (narrative generation, the evaluation harness) to defer to `root_cause.status` for the matched/not-matched question and use `NegativeEvidenceReport` specifically for candidate-level diagnostic detail.

Decision: A failing `fee_rule` constraint/hypothesis is only attributed to "fee_mismatch" when the applicable `FeeRule` prescribes a non-trivial deduction (`mdr_percent > 0` or `fixed_fee > 0`). Under a zero-rate rule (UPI, in this dataset), a failing fee check is instead attributed to `relationship_consistency` / `unexplained_difference`.
Reason: Under a zero-fee rule, `verify_fee_consistency`'s "expected" value collapses to the same figure `relationship_consistency`'s self-check computes, so both "fail" for the same underlying reason whenever a settlement's own net_amount is corrupted (M1's `unexplained_difference` archetype) — without this guard, that archetype was misclassified as `fee_mismatch` (caught via the empirical 0-category-mismatch check against ground truth before this milestone was marked done).
Alternatives considered: Checking self-consistency before fee-consistency unconditionally.
Why rejected: Would then misclassify the real M1 adversarial `fee_mismatch` cases (card method, non-trivial rule) as `unexplained_difference` instead, since those also fail self-consistency by construction. The rule-magnitude check is the one signal that correctly separates both cases.

Decision: `partial_settlement` vs. `under_settlement` classification uses a documented magnitude heuristic — settlement covers ≥85% of the payment → `under_settlement`, otherwise `partial_settlement`.
Reason: M1's dataset does not encode any structural difference between these two archetypes (both are a single settlement, zero-fee, confirmed by bank credit, covering less than the payment) — only the magnitude of the shortfall differs by generator design (partial: 55–75% covered; under: 92–96% covered), and 85% sits cleanly in the non-overlapping gap between those two ranges.
Alternatives considered: Classifying both identically as `partial_settlement`; inventing a new dataset field to distinguish them (would have meant modifying M1, which must be preserved).
Why rejected: Classifying both the same would have failed the classification-accuracy metric against ground truth for 8 real records; modifying M1 was out of scope for this milestone. Documenting the heuristic and its exact threshold, rather than silently guessing, satisfies "do not modify ground truth, investigate and document disagreements instead."

Decision: The risk-priority formula is `risk_score = |financial_delta| × confidence_deficit × sla_aging_factor`, with confidence_deficit fixed per root-cause status (0.00 VERIFIED / 0.40 PARTIALLY_EXPLAINED / 0.60 CONTRADICTED / 0.80 AMBIGUOUS / 1.00 UNEXPLAINED) and sla_aging_factor scaling linearly from 1.0 to 2.0 over 30 days relative to the dataset's own latest record.
Reason: The project's own documented intent (context pack §12 Value-at-Risk prioritization, PROJECT_PLAN.md M15) names amount, confidence, and aging/business-impact as inputs but does not fix an exact formula; the M3 brief explicitly requires not hard-coding an undocumented metric.
Alternatives considered: Amount alone; amount × a single ad-hoc "severity" scalar with no stated meaning.
Why rejected: Amount alone would let a large but well-understood (VERIFIED) exception outrank a smaller, genuinely uncertain one, which the brief explicitly warns against. This formula is now the one place the weighting lives (`app.engines.risk.scoring`), open to retuning once real prioritization feedback exists.
Date: 2026-08-25

Decision: `decompose_discrepancy`'s components (refund, fee+tax) are computed independently and summed additively against a single `observed` figure (the settlement's confirmed CREDIT amount only, not netted against any separate debit).
Reason: This is correct and sufficient for every case M1's actual dataset produces, since no archetype combines a non-trivial fee deduction with a refund on the same record.
Alternatives considered: Netting matched refund debits directly into `observed` so combined fee+refund cases decompose correctly in one pass.
Why rejected: Would require reworking the observed/expected contract for a case that doesn't exist in the current dataset; documented as a known limitation instead, to be revisited if a future dataset or milestone actually combines both deduction types on one record (see backend/tests/exceptions/test_hypotheses_and_decomposition.py's docstring for the precise arithmetic tension).

Alternatives considered: Exposing it as a normal tool, relying on the controller to only call it once per hypothesis.

Decision: Two real, non-cosmetic safety gaps were found and fixed empirically while building this milestone, both via the 300-record evaluation surfacing non-zero false auto-resolutions before any test asserted 0% — recorded here in full since they materially shaped the verifier/policy design:
  (1) `TIMING_DELAY`'s verifier originally checked only date proximity, not amount — this let the real M1 adversarial `fee_mismatch` case (whose settlement genuinely falls inside the timing tolerance window) verify as a timing delay and reach `SAFE_TO_RESOLVE`, a false auto-resolution on the exact adversarial case M1 was built to catch.
  (2) Single-settlement hypothesis verifiers (refund/fee/timing/reference-error) did not check for a `reversed` settlement status, a sibling duplicate settlement genuinely linked to the same payment, or a rival unlinked candidate — this let real `duplicate` and `reversed_transaction` cases verify and reach `SAFE_TO_RESOLVE` by checking only the one settlement the mock happened to name, in isolation.
Reason for recording this in full: both gaps are exactly the shape of bug M2's own non-negotiable ambiguity rule and M3's `reversed_transaction`/`duplicate` policy finding were designed to prevent at the deterministic layer — building the AI layer on top very nearly reintroduced them at a new layer that didn't yet have the equivalent guard, which is precisely why the brief's own instruction to run the full 300-record evaluation and treat a non-zero false-auto-resolution rate as a stop condition mattered here, not just as a formality.
Fix: (1) `_verify_timing` now requires the confirmed bank-credited amount to also equal the payment amount exactly. (2) A new shared guard, `_single_settlement_selection_conflict` (`app.ai.verifier`), blocks all four single-settlement hypothesis types whenever the settlement is reversed, has a genuine sibling, or has an unresolved rival candidate; separately, `app.ai.policy.NEVER_AUTO_RESOLVE_CATEGORIES` enforces the same categorical rule on the no-AI path (M3-VERIFIED `reversed_transaction`/`duplicate` exceptions that never reach the AI at all).
Date: 2026-08-27

Decision: The policy engine (`app.policy.engine`) uses a fixed four-tier precedence — BLOCK/SAFETY > MANDATORY_APPROVAL > RISK > AUTO_ELIGIBILITY — evaluated top-to-bottom, with the first tier that fires deciding the outcome (all tiers are still recorded in `rules_evaluated` regardless of which one decides).
Reason: This is the M5 brief's own explicitly recommended precedence, and it's what makes the policy-conflict example (a verified fee mismatch that's ALSO over the exposure threshold) resolve safely to `HUMAN_REVIEW` rather than depending on incidental rule-definition order.
Alternatives considered: A flat rule list evaluated in declaration order with no tier structure; a scoring/voting system where rules contribute weighted votes toward a decision.
Why rejected: A flat list makes safety depend on the order rules happen to be written in, which the brief explicitly warns against ("do not allow rule ordering to accidentally create unsafe behaviour"). A voting system could let enough weak "auto-resolve" signals outvote a single strong safety concern, which is exactly backwards for a financial system — safety rules must have absolute, not proportional, precedence.
Date: 2026-08-27

Decision: `missing_transaction` is deliberately excluded from `app.services.resolution_service.NEVER_AUTO_RESOLVE_CATEGORIES` and is instead recognized by a dedicated tier-0 check (ahead of BLOCK) mapping it directly to `UNRESOLVED`.
Reason: Found empirically — including it in the generic "always human review" category set let `POLICY-CATEGORY-001`/`POLICY-UNEXPLAINED-001` (both MANDATORY_APPROVAL-tier rules) fire first and mislabel all 12 real `missing_transaction` cases as `HUMAN_REVIEW`, contradicting `ground_truth.expected_action` (`unresolved`) for every one of them. "Nothing exists yet to review" and "something exists but needs a human's judgment" are different kinds of outcomes, not degrees of the same one.
Alternatives considered: Leaving `missing_transaction` in the shared category-exclusion set and accepting `HUMAN_REVIEW` as "close enough" to `unresolved`.
Why rejected: Would have silently collapsed a real, ground-truth-encoded five-way distinction back down to a three-way one, exactly the kind of information loss M4's own richer `RecommendedAction` vocabulary (including `UNRESOLVED`) was introduced to avoid in the first place.

Decision: `app.services.decision_service.run_decision_pipeline` is a new, additive orchestrator that makes M5's `evaluate_policy()` the single decision authority for EVERY exception, AI-assisted or not — replacing the previous state where `app.services.ai_exception_service.resolve_one` computed its own final decision via `app.ai.policy.decide_final_outcome()` independently of M5's policy engine for AI-assisted exceptions.
Reason: Before M6, an AI-assisted exception's fate was decided by `app.ai.policy` alone; a non-AI-assisted exception's fate was decided by `app.policy.engine` alone. These happened to agree on every case in the real 300-record dataset, but were two separate authorities, not one architecturally unified decision boundary — exactly the kind of gap M6's "one trust chain" framing and its self-challenge feature need to not exist, since the self-challenge rule (conflicting_evidence) only has one place to plug into if there is only one policy authority.
Alternatives considered: Leaving the two paths separate and adding the audit ledger/contradiction logic to each independently.
Why rejected: Would have meant either duplicating the self-challenge integration in two places (drifting apart over time) or picking one path arbitrarily to wire it into, leaving the other silently unprotected. Unifying them is also a smaller total diff than maintaining two audited paths, and `ai_exception_service`/`resolution_service` themselves remain unchanged and independently correct/tested — this is a new integration layer on top, not a rewrite.
Date: 2026-08-27

Decision: The self-challenge rule (Phase 11) is implemented by setting the EXISTING `PolicyInput.conflicting_evidence` field to `True` when `app.challenge.contradiction.has_unresolved_contradiction()` finds a contradicted hypothesis, rather than adding a new field or a new policy rule.
Reason: M5's `PolicyInput` already had a `conflicting_evidence: bool` field and a dedicated `POLICY-CONFLICT-001` rule in the `MANDATORY_APPROVAL` tier — built for exactly this kind of signal, just never fed by a real caller until now. Reusing it means the self-challenge integration required zero changes to `app.policy.engine` itself.
Alternatives considered: Adding a new `PolicyDecisionType.CHALLENGED` outcome, or a new dedicated policy rule/tier specifically for AI-hypothesis contradictions.
Why rejected: Would have created a second code path for what is semantically the same situation M5 already modeled ("evidence conflicts, so don't auto-resolve"), and would have required re-verifying the whole policy precedence table for interactions with the new rule. Reusing the existing field/rule is both smaller and provably safe, since M5's precedence tests already cover `POLICY-CONFLICT-001`'s behavior.
Date: 2026-08-27

Decision: `app.audit.ledger.AuditLedger` has no `update`/`delete` method defined anywhere — not "unauthorized for all actors," structurally absent from the class.
Reason: Mirrors the exact discipline M4 used for `test_hypothesis` not being offered as a callable tool (`app.ai.tools.TOOL_REGISTRY`) — some boundaries are safer made structurally impossible to cross than merely gated by a permission check that could be misconfigured or bypassed by calling a lower-level API directly.
Alternatives considered: Implementing `update`/`delete` methods and gating them behind `Capability.APPEND_AUDIT`-style authorization checks (with no actor ever granted the corresponding capability).
Why rejected: A method that exists but is never authorized is still an attack surface (a future bug in the authorization check would silently reopen it); a method that doesn't exist has no such risk. This is why `Capability.UPDATE_AUDIT`/`Capability.DELETE_AUDIT` don't exist as enum values either — there is nothing for such a capability to gate.
Date: 2026-08-27

Decision: `verify_chain()` recomputes each event's hash using that event's OWN stored `schema_version`, never the current `SCHEMA_VERSION` module constant.
Reason: If the hashing schema ever changes in a future milestone, an old event hashed under an older schema must still reproduce its original, already-stored hash — otherwise every historical event would spuriously fail verification the moment the schema constant changes, which would make the audit ledger fail-unsafe in exactly the way it exists to prevent.
Alternatives considered: Always using the current `SCHEMA_VERSION` constant for recomputation.
Why rejected: Would make the chain's validity depend on the CURRENT code version rather than the conditions under which each event was actually written — the opposite of what an audit trail is supposed to guarantee.
